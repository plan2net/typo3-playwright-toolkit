End-to-end tests for TYPO3, with {{ c.text }}.

Every spec file gets its own database, cloned from a prepared template in milliseconds. Files run at the same time without sharing data, so one test can never break another. And the content comes from the real TYPO3 backend, not from SQL fixtures, so your tests see pages the way an editor would build them.

For TYPO3 projects that run on DDEV (optional).

Two people, two files

Git has no trouble with two people working in separate files. It has no answer for two people picking the same ID, which is what a shared fixture file asks them to do.

tests/fixtures/pages.sql CONFLICT 
<<<<<<< HEAD
INSERT INTO pages (uid, pid, title, slug)
VALUES (42, 1, 'Newsroom', '/newsroom');
=======
INSERT INTO pages (uid, pid, title, slug)
VALUES (42, 1, 'Careers', '/careers');
>>>>>>> feature/careers
Both sides look right. Keep either one and a test loses its page — the ID is the reference.

Each test builds its own pages through the backend, so a new test is a new file and nobody else’s lines move.

Your fixture manifest stays at what every test genuinely needs: a site root and a TypoScript template. It stops growing with the suite, and the merge conflicts over IDs stop with it.

One file is one scenario

A setup that builds content once, and the tests that read it. Between the two sits one header, and nothing routes it: Apache and nginx hand X-Playwright-Test-Id to PHP by themselves. No SetEnvIf mapping it to an environment variable, and nothing to keep in sync when it changes.

Why not click through the backend?

Playwright could open the TYPO3 backend and fill in the forms the way an editor does. That is slow, several seconds per record, and fragile: the markup changes between TYPO3 versions and FormEngine builds the fields from your TCA, so a selector that works today can stop working after an update. You gain little for it. The builders post the same fields and the same request token to the route the form itself uses.

When TYPO3 refuses a record

A save that TYPO3 rejected still answers like a save. The builder reads that answer and stops on the line that saved, naming the record and the reason. A failed test also brings along what TYPO3 wrote to its log while it ran — refused records, uncaught exceptions, anything logged as an error — attached to the report as typo3-errors.json.

tests/news.spec.ts
import {
    defineScenario, expect, expectScreenshot,
    imageCrop, runAccessibilityScan,
} from '@plan2net/typo3-playwright-toolkit'

export const test = defineScenario(async ({ builders }) => {
    const page = await builders.page()
        .withTitle('Newsroom').withSlug('/newsroom').create()

    // Every TYPO3 core CType already has a builder.
    await builders.content().onPage(page.id).ofType('textmedia')
        .configure((element) => element.withHeader('Latest'))
        // The sys_file_reference rows are written for you.
        .withFileReferences('assets', [1, 2], {
            crop: imageCrop({ ratio: '16:9' }),
        })
        .create()

    return { slug: page.slug }
})

test('editor publishes a news page', async ({ page, state }) => {
    await page.goto(state.slug)

    await expect(page.getByRole('heading', { name: 'Latest' }))
        .toBeVisible()

    // Fonts, images and animations have settled.
    await expectScreenshot(page, 'newsroom')

    // axe, on the page as the test left it.
    await runAccessibilityScan(page)
})
Content is posted to /typo3/record/edit — the route the backend itself uses on save, request token included.

When a test fails, open its backend

A screenshot tells you that something broke, but not what the database looked like at that moment.

That is why a failed file keeps its database instead of dropping it, and ddev playwright-inspect prints a signed link for each one. Open it and you are inside the TYPO3 backend of that exact run — already logged in, page tree intact, content exactly as the test left it, the frontend one click away. The scenario name and its test ID sit beside the site name, so two open tabs are never confused.

Your suite already built a demo site

Every scenario builds content. ddev playwright-replay runs all of them into one database instead of one per test file, each scenario in its own sysfolder, and prints a single link into that backend.

So the pages your tests need are also pages people can look at. Show a client every content element, or check a template change against all of them at once. Nobody had to build any of it by hand.

There is a whole TYPO3 project in the repository, and CI reinstalls it on every push

Site configuration, seed fixture, web-server binding, Playwright config: a working project rather than a snippet. The setup instructions cannot go stale, because CI executes them.

The next upgrade tells you what broke

Your content is built through the backend’s own save route, so a TYPO3 release that renames a field fails a test instead of slipping past. And when one fails, its database is still there — one signed link and you are inside that backend, on that content, looking at what the test saw.
